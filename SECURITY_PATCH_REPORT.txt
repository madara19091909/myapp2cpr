التقرير النهائي لتعديلات أمن لعبة مزرعتي
========================================

نطاق العمل
----------
هذه النسخة تنقل مصدر الحقيقة للاقتصاد والتوقيت من تطبيق Flutter إلى Firebase
Cloud Functions. لا تعني هذه المراجعة أن المشروع نُشر أو خضع لاختبار اختراق حي؛
هي نتيجة تعديل الكود وفحصه ساكناً وتشغيل اختبارات منطق الخادم المتاحة.

النتيجة الأهم
-------------
أضيفت طبقة خادم حقيقية داخل functions/ وربط تطبيق Flutter بها. لم يعد التطبيق
يرسل رصيداً أو مخزوناً ليطلب من Firebase حفظه؛ بل يرسل اسم العملية ومعطياتها
المحدودة، والخادم يقرأ الحالة الحالية ويحسب السعر والضريبة والوقت والنتيجة ثم
يحفظ الحالة الجديدة باستخدام Firebase Admin SDK.

الإصلاحات المطبقة
-----------------
1. اقتصاد اللعبة أصبح Server-authoritative في العمليات التالية:
   شراء وبيع البذور، شراء وبيع الحيوانات، شراء الماء والعلف، إطعام الحيوانات،
   شراء الأدوات والمباني والديكور والتأمين، فتح الأراضي، الزراعة والسقي والحصاد،
   بيع المحاصيل والمنتجات، تحصيل الحيوانات، التصنيع، المكافأة اليومية، صندوق الحظ،
   المهام اليومية، الإنجازات، تغيير الاسم وتحديث حالة اللعبة.
   الخادم لا يقبل السعر أو قيمة المكافأة من الهاتف؛ بل يستخرجها من تعريفاته.

2. الوقت الحساس يُحسب في الخادم باستخدام وقت التنفيذ الموثوق والمنطقة الزمنية
   Asia/Baghdad. يشمل ذلك نضج المحاصيل وإنتاج الحيوانات والتصنيع والمكافآت اليومية
   والأحداث الأسبوعية والموسمية والطقس. نتيجة صندوق الحظ تستخدم مولّد عشوائي
   تشفيري داخل الخادم، وليس ساعة الهاتف أو modulo.

3. أضيفت Cloud Functions callable:
   - bootstrapGame: إنشاء/تحميل حالة اللاعب وتهيئة المستندات المشتقة.
   - applyGameAction: تنفيذ عملية لعبة واحدة داخل معاملة Firestore.
   - adminUpdatePlayer: تعديلات الإدارة المحدودة مع سبب وسجل تدقيق.

4. أضيفت حماية إعادة إرسال العمليات:
   كل عملية من العميل تتطلب requestId، ويُحفظ إيصال العملية في
   gameActionReceipts لمنع تنفيذ الطلب نفسه مرتين. أضيف حد 120 عملية لعب في الدقيقة
   لكل UID، و30 طلب تهيئة في الدقيقة لكل UID. الطلبات الفاشلة تُستهلك من حد المعدل.

5. قواعد Firestore تمنع العميل من إنشاء أو تعديل أو حذف users/{uid} وgameStates
   وpublicProfiles وfarmSnapshots وسجلات الإيصالات وحدود المعدل وسجلات تدقيق الإدارة.
   الحالة الاقتصادية لا يكتبها إلا Admin SDK داخل Cloud Functions.

6. فصلت بيانات المزرعة عن بيانات الهوية العامة:
   publicProfiles يحتوي UID والاسم ووقت التحديث فقط. farmSnapshots يحتوي الأراضي
   ويُقرأ من المالك أو الأدمن أو صديق مقبول فقط.

7. تشددت قواعد الصداقة:
   إنشاء طلب الصداقة يتطلب إنشاء الطرفين المقابلين في batch/transaction، وقبول الصداقة
   يتطلب إنشاء السجلين معاً، كما يتطلب حذف العلاقة حذف السجلين المتبادلين معاً. والاسم
   يُطابق الاسم العام، وقبول الصداقة يتطلب طلباً وارداً معلقاً ويُنشئ سجلّي الصداقة
   المتبادلين ذرياً. تحديث سجلات الصداقة مباشرة ممنوع.

8. شددت صلاحيات الإدارة:
   الأدمن العادي لا يستطيع إدارة مجموعة admins. إضافة أو حذف عضوية الأدمن تتطلب
   custom claim باسم superadmin. تعديل بيانات اللاعبين يمر عبر callable محدود
   بالحقول والمديات ويتطلب سبباً، ويُسجل قبل/بعد التغيير في adminAuditLogs.

9. أضيف Firebase App Check إلى Android (Debug provider أثناء التطوير وPlay Integrity
   في Release) وإلى لوحة Web عبر reCAPTCHA v3. جميع Cloud Functions تفرض App Check.
   تسجيل التطبيقات والمفاتيح وEnforcement الفعلي ما زال يحتاج إعداد Firebase Console.

10. الحسابات تتطلب بريد Firebase موثقاً. AuthGate يمنع دخول الحساب غير الموثق،
    وقواعد Firestore والدوال تتحقق من email_verified.

11. الحفظ المحلي صار كاش عرض مؤقت فقط. لا يُرفع SharedPreferences إلى الحساب ولا
    يتغلب توقيته على الحالة السحابية. عند فشل تحميل الحالة من الخادم لا تُفتح اللعبة
    بحالة افتراضية ولا يُكتب الحفظ المحلي فوق السحابة.

12. الحسابات القديمة:
    عند أول bootstrap تُستورد بيانات users/{uid} إلى gameStates، لكن تُوسم
    legacyUnverified. تُصفّر طوابير التصنيع والمؤقتات القابلة للتلاعب ويُعاد ضبط
    أوقات المحاصيل والحيوانات، وتُمنع العمليات الاقتصادية والمكافآت إلى أن يراجع
    الأدمن الأرصدة والأصول القديمة ويعتمد الحساب. لا يمكن إثبات نزاهة أرصدة تاريخية
    كان العميل يستطيع كتابتها قبل هذا الإصلاح. التحقق اليدوي لا ينبغي أن يكون آلياً.

13. لوحة الإدارة:
    التعديلات الاقتصادية تمر عبر adminUpdatePlayer، وتحرير JSON المباشر معطل،
    وعرض قيم الاقتصاد لا يظهر في القائمة العامة. أزيل إدخال المحتوى الديناميكي عبر
    innerHTML واستُخدمت textContent وعناصر DOM.

14. GitHub Actions:
    لم يعد يحذف مجلد الاختبارات، ويشغل lint واختبارات Cloud Functions قبل بناء APK.
    تم تحديث Node إلى 22 وضبط Firebase Functions runtime على nodejs22.

ما تعذر اختباره
---------------
- Flutter وDart غير مثبتين هنا؛ لم أتمكن من تشغيل flutter pub get أو flutter analyze
  أو flutter test أو إنتاج APK.
- Firebase CLI وFirestore Emulator غير متاحين؛ لم أتمكن من التحقق التنفيذي من
  قواعد Firestore أو نشر Functions/Rules إلى مشروع Firebase الحي.
- لم يتم الاتصال بمشروع Firebase الحي أو قراءة بيانات اللاعبين الحقيقية.
- محاولة إنشاء package-lock عبر npm توقفت بسبب فشل DNS للوصول إلى registry.npmjs.org؛
  لذلك لم تتم إضافة lockfile. الإصدارات المباشرة في package.json مثبتة بأرقام محددة.
- لم أختبر XSS أو MFA أو Play Integrity على أجهزة وحسابات حقيقية.

المخاطر والخطوات التي ما زالت مطلوبة قبل اعتبار الإصلاح منشوراً
------------------------------------------------------------
1. نشر Cloud Functions وقواعد Firestore على مشروع myapp2-62246.
2. إعداد Android App Check وWeb reCAPTCHA ومفاتيح تطبيق Web؛ توجد قيم REPLACE_ في
   admin/index.html يجب استبدالها قبل استخدام لوحة الإدارة.
3. تشغيل scripts/migrate_public_profiles.js بعد أخذ نسخة احتياطية وقبل فتح
   publicProfiles للمستخدمين على القواعد الجديدة.
4. نشر APK الجديد وتنسيق نشر القواعد بحيث لا تبقى نسخ التطبيق القديمة تحاول كتابة
   users/{uid} أو publicProfiles بالبنية القديمة.
5. مراجعة كل حساب legacyUnverified يدوياً. الحساب غير المراجع لن يتمكن من اللعب
   اقتصادياً بعد الترقية. إذا تعذر إثبات نزاهة الحساب فيجب تصفير/تعديل بياناته قبل
   اعتماده، وليس الضغط على اعتماد جماعياً.
6. تفعيل MFA لحسابات الإدارة بعد تجهيز تدفق تسجيل دخول يدعم تحدي MFA؛ لوحة Web
   الحالية لا تحتوي بعد على واجهة إكمال تحدي MFA.
7. تثبيت GitHub Actions على commit SHAs موثوقة، وإضافة اختبارات Dart وقواعد Emulator.
8. تفعيل سياسة TTL في Firestore لحقل expireAt ضمن مجموعة gameActionReceipts حتى
   تُحذف إيصالات منع التكرار القديمة بعد 30 يوماً. إذا لم تُفعّل السياسة فستبقى
   الإيصالات المخزنة وتزيد مع الاستخدام.
9. يتطلب نشر Cloud Functions خطة Firebase/Google Cloud مدفوعة مناسبة (Blaze)،
   ويجب ضبط تنبيهات الميزانية ومراقبة استهلاك الاستدعاءات.

الحكم النهائي
-------------
على مستوى الكود، نُقلت عمليات الاقتصاد والوقت إلى Cloud Functions وأُغلقت كتابة
العميل المباشرة للحالة الاقتصادية في القواعد الجديدة. اختبارات منطق الخادم نجحت.
لكن النسخة ليست منشورة ولم تُختبر على Firebase Emulator أو APK حقيقي في هذه البيئة؛
لذلك لا يمكن وصفها بأنها شهادة أمان أو ضمان نهائي قبل إكمال خطوات النشر والاختبار
المذكورة أعلاه.
